# 테스트 유형 선택 기준

테스트 작성/검토 시 이 문서를 기준으로 유형을 판단.
**유지보수 비용 최소화**가 선택의 최우선 기준.

---

## 결정 트리

```
어떤 대상을 테스트하는가?
│
├─ 공통 컴포넌트 / 커스텀 훅 / 유틸 함수
│   └─ 다른 모듈 의존성이 거의 없고 독립적으로 동작하는가?
│       ├─ Yes → 단위 테스트
│       └─ No  → 통합 테스트 고려
│
├─ 비즈니스 로직 (여러 컴포넌트 조합, API 연동)
│   └─ 통합 테스트
│
├─ 전체 워크플로우 (로그인, 결제, 리다이렉트 등)
│   └─ 통합 테스트로 작성 시 모킹이 지나치게 많아지는가?
│       ├─ Yes → E2E 테스트
│       └─ No  → 통합 테스트로 충분
│
└─ UI 시각적 일관성 유지 (CSS, 레이아웃 변경 감지)
    └─ 시각적 회귀 테스트
```

---

## 유형별 장단점

### 단위 테스트 (Vitest + RTL)

| | |
|--|--|
| **장점** | 빠른 실행, 낮은 유지비용, 명확한 실패 지점 파악 |
| **단점** | 전체 워크플로우/모듈 간 통합 이슈 발견 불가 |
| **적합** | 공통 컴포넌트(TextField 등), 커스텀 훅, 공통 유틸/헬퍼 |
| **비적합** | 비즈니스 로직, API 연동이 핵심인 기능 |

> 아주 간단한 유틸 함수는 테스트 생략 가능.
> 해당 함수가 포함된 모듈의 통합 테스트에서 함께 검증하는 것이 더 효율적.

---

### 통합 테스트 (Vitest + RTL + MSW)

| | |
|--|--|
| **장점** | 비즈니스 로직에 가까운 검증, 모듈 간 상호작용 오류 발견, 실제 사용자 시나리오와 유사 |
| **단점** | 모킹 과의존 위험, 전체 워크플로우 검증 한계 |
| **적합** | 특정 상태 기준 컴포넌트 조합, API 연동 컴포넌트, 상위-하위 컴포넌트 렌더링/동작 |
| **비적합** | 구매 성공/실패처럼 모킹에만 의존해야 하는 중요 플로우 |

> 모킹은 최소화. API 응답은 MSW로 처리.
> 중요 시나리오(결제, 인증 등)를 모킹에만 의존하면 신뢰도 하락.

---

### E2E 테스트 (Playwright)

| | |
|--|--|
| **장점** | 실제 앱 전체 흐름 검증, 모킹 불필요, 가장 높은 신뢰도 |
| **단점** | 느린 실행 속도, 결정성 보장 어려움(flaky), 높은 유지비용, 유관부서 협의 필요 |
| **적합** | 로그인/인증, 권한 체크 + 리다이렉트, 결제 등 전체 워크플로우 |
| **비적합** | 단순 컴포넌트 동작, 빠른 피드백이 필요한 로직 |

> 통합 테스트로 작성 시 모킹이 지나치게 많아지는 시나리오가 E2E의 신호.
> API는 가능하면 모킹 안 함. 테스트 전용 DB/계정 별도 구성, 유관부서 협의 필수.
> 실패 케이스 등 재현 어려운 경우는 예외적으로 `page.route()` 모킹 허용.

---

### 시각적 회귀 테스트 (Vitest Browser Mode)

| | |
|--|--|
| **장점** | CSS·레이아웃 변경 감지, 기능 테스트로는 잡기 어려운 시각적 버그 발견 |
| **단점** | 높은 유지비용, 픽셀 비교 flaky 위험, 환경(OS/브라우저) 차이 관리 필요 |
| **적합** | 디자인 시스템 컴포넌트, 레이아웃 변경이 잦은 UI |
| **비적합** | 기능 동작 검증, 비즈니스 로직 |

> DOM 스냅샷(`toMatchSnapshot`)은 CSS 변화를 감지 못함. 실제 시각 검증은 이미지 스냅샷 사용.
> 이미지 관리는 Docker(Linux) 환경에서 단일 기준 이미지 생성 권장.

## 전략 선택

### 테스트 트로피 — 일반 서비스 앱 권장

```
E2E      ▲ 소수
통합     ████████ 다수 (핵심)
단위     ████ 중간
Static   TypeScript + ESLint
```

비즈니스 로직 검증 = 통합 테스트 중심.

### 테스트 피라미드 — UI Kit / 컴포넌트 라이브러리 권장

```
E2E      ▲ 소수
통합     ████ 중간
단위     ████████ 다수 (핵심)
```

공통 컴포넌트 기능 검증 = 단위 테스트 중심.

## 요약표

| 유형 | 속도 | 유지비용 | 신뢰도 | 주요 한계 |
|------|------|----------|--------|-----------|
| 단위 | ⚡ 빠름 | 낮음 | 중 | 전체 흐름 검증 불가 |
| 통합 | 보통 | 중간 | 높음 | 모킹 과의존 위험 |
| E2E | 🐢 느림 | 높음 | 매우 높음 | flaky, 유관부서 협의 |
| 시각적 회귀 | 보통 | 높음 | 중 | 환경 차이, 픽셀 flaky |
