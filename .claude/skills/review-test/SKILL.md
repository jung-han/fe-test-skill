## 대상 프로젝트 확인

`package.json`에 `react` 의존성이 없으면 이 스킬을 실행하지 않는다.

---

## 실행 절차

### Step 1. 프로젝트 설정 파악

`project-config.md`를 먼저 찾는다.
없으면 `package.json`, `vitest.config.*` 등을 읽어 파악한다.

---

### Step 2. 리뷰 계획 수립

**범위가 명시된 경우**: 해당 파일 또는 폴더를 대상으로 한다.

**범위가 명시되지 않은 경우**:

전체 테스트 파일 목록을 스캔해 파일명을 모두 나열한다 (`*.test.tsx`, `*.spec.tsx`, `*.test.ts`, `*.spec.ts`, `e2e/` 등).

나열된 목록을 기준으로 최대 50개를 선별한다. 선별 기준은 AI가 판단한다:
- 파일 총 수가 50개 이하면 전부 포함한다
- 50개 초과면 아래 기준으로 중요도 판단:
  - 테스트 유형 다양성 (단위/통합/E2E/시각적 회귀 고루 포함)
  - 줄 수 (복잡도가 높은 파일 우선)
  - 경로 다양성 (components/hooks/pages/utils/e2e 고루 포함)
  - 모킹 밀도 (vi.mock/MSW 사용 파일 우선 — 오용 가능성 높음)

선별 후 검수 시작 전에 리뷰 계획을 출력한다:

```
리뷰 계획: 총 N개 파일
- components/: N개
- hooks/: N개
- pages/features/: N개
- utils/: N개
- e2e/: N개

선별 이유: (50개 초과 시에만) 한 줄 설명
```

사용자가 범위를 조정하고 싶으면 이 시점에 요청한다. 확인 없이 바로 진행한다.

---

### Step 3. 검수

선정된 파일을 하나씩 읽고, `@references/review-checklist.md`의 검수 순서대로 평가한다.
각 관점에서 참조 문서의 ❌ 패턴 및 원칙 위반을 확인한다.

특히 시나리오 도출 관점(checklist의 #3)은 `@references/scenario-design.md`의 7가지 도출 기법을 기준으로 평가한다 — main flow만 검증하고 alternative/exception 누락, ECP/BVA 경계 누락, Decision Table 없이 즉흥 작성된 다중 조건 등.

---

### Step 4. 결과 출력

아래 구조의 보고서를 **파일로 저장**한 뒤, 동일 내용을 채팅에도 출력한다.

**저장 경로**: 검토 대상 루트(범위가 폴더면 그 폴더, 파일이면 부모 폴더)에 `REVIEW-REPORT-{YYYY-MM-DD}.md`.
같은 날짜 파일이 이미 있으면 `-2`, `-3` 식으로 suffix를 붙인다. 덮어쓰지 않는다.

저장 후 첫 줄에 저장 경로를 알린다 (예: `보고서 저장: tests/.../REVIEW-REPORT-2026-05-05.md`).

보고서는 4개 섹션으로 구성한다: ① 요약 → ② 반복 패턴 → ③ 파일별 액션 → ④ 전체 권장.

---

#### ① 검수 결과 요약 (표)

```markdown
## 요약

| 심각도   | 건수 |
|----------|------|
| Critical | N    |
| Major    | N    |
| Minor    | N    |

검토 파일: N개
```

문제가 없으면: `검토 파일: N개 | 이슈 없음`

---

#### ② 반복 패턴 (❌/✅ 코드 예시)

2건 이상 반복되는 패턴은 파일별 항목에서 풀어쓰지 않고, 이 섹션에 패턴 번호를 부여해 한 번만 설명한다.
각 패턴은 **현상 1줄 + ❌ 코드 + ✅ 코드 + 왜 1~2줄 + 적용 위치 목록**으로 구성한다.

"왜" 줄은 규칙을 외우게 하지 말고 **이유로 납득시키는 것**이 목적이다 — 어떤 실패/유지보수 비용을 막는지를 짧게 명시한다.

```markdown
## 반복 패턴

### 패턴 #1 — [패턴명] (N건)
[한 줄 현상 설명]

❌ 안티패턴:
\`\`\`ts
// 실제 코드 또는 대표 예시
\`\`\`

✅ 권장:
\`\`\`ts
// 수정 코드
\`\`\`

**왜**: [1~2줄. 이 패턴이 왜 문제인지 / 권장안이 왜 나은지.]

**적용 위치**: `파일A:L12`, `파일B:L34`, ...
```

---

#### ③ 파일별 액션 아이템 (표)

파일마다 표로 출력한다. Critical → Major → Minor 순.
반복 패턴은 `패턴 #N 참조`로 표기하고, 단발성 이슈만 풀어쓴다.

```markdown
## 파일별 액션 아이템

### 파일경로

| 심각도   | 위치   | 문제 / 수정 |
|----------|--------|-------------|
| Critical | L24-28 | 단발성 이슈는 한 줄로. 수정 방향 포함. |
| Major    | L22-53 | 패턴 #1 참조 |
| Minor    | L20    | 단발성 이슈. |
```

**작성 규칙**:
- 표 셀은 한 줄. 수정 코드가 길면 표 아래 코드블록으로 footnote 처리.
- 같은 파일 내 동일 패턴 반복 시 표 한 행에 모든 위치를 묶음 (`L12, L34, L56`).
- 테스트 유형 자체가 잘못된 경우 `@.claude/rules/test-selection.md` 기준으로 적합한 유형을 제안한다.
- 이슈 없는 파일은 `이슈 없음`으로 한 줄 표시 (표 생략).

---

#### ④ 전체 권장 (표)

여러 파일에 걸친 구조적 권장 사항(setup 보강, 헬퍼 추출 등)을 표로 정리.

```markdown
## 전체 권장

| 우선순위 | 항목 | 조치 |
|----------|------|------|
| 1 | setupTests 보강 | `afterAll(() => vi.restoreAllMocks())` 추가 |
| 2 | ... | ... |
```

심각도 기준은 `@references/review-checklist.md`를 따른다.
